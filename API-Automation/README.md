# Velocity JSON API automation

Automation for the **Velocity Clearing JSON API Specification 1.4** — the seven
HTTPS endpoints behind Velocity Locate Services.

This suite targets the **Dev/Test environment only**. The production host is
recorded in `Config/env.js` purely so the guard can refuse it by name: these
scenarios place real locate orders, and `API_BASE_URL` pointing anywhere on
`velocityclearing.llc` throws before the first request.

It lives beside `UI-Automation/` and shares the same runner (Playwright +
playwright-bdd), the same reporter (Allure) and the same Gherkin conventions,
but shares no code with it. Nothing here launches a browser — no step uses the
`page` fixture, so the whole suite runs at HTTP speed.

---

## Quick start

```powershell
# 1. Credentials - no defaults, by design (see "Configuration" below)
$env:VELOCITY_API_USER     = '<preassigned UserID>'
$env:VELOCITY_API_PASSWORD = '<preassigned password>'
$env:VELOCITY_MPID         = '<market participant id>'
$env:VELOCITY_TRADER       = '<trader id>'

# 2. Run
npm run test:api:smoke     # @Smoke scenarios only
npm run test:api           # the full API suite
npm run test:api:ci        # full suite with the Allure reporter

# Useful one-offs
$env:API_LOG = '1'; npm run test:api        # print every request/response
npx playwright test --project=api --grep @Quote
```

Without the four required variables the authenticated scenarios **skip** rather
than fail, so a run on a machine with no credentials reports honestly instead of
producing a wall of red.

## Configuration

Required — the suite throws naming the variable if one is missing:

| Variable                 | Meaning                                    |
| ------------------------ | ------------------------------------------ |
| `VELOCITY_API_USER`      | preassigned UserID (spec 1.3)              |
| `VELOCITY_API_PASSWORD`  | preassigned password (spec 1.3)            |
| `VELOCITY_MPID`          | market participant id on quote/order calls |
| `VELOCITY_TRADER`        | trader id on quote/order calls             |

Optional:

| Variable                   | Default                                  | Meaning |
| -------------------------- | ---------------------------------------- | ------- |
| `API_BASE_URL`             | `https://betapi.velocitycapitalllc.com/json` | another dev/test host; production is refused |
| `API_TIMEOUT_MS`           | `30000`                                  | per-request timeout |
| `API_LOG`                  | off                                      | `1` prints every request/response (password and token redacted) |
| `API_WORKERS`              | `1`                                      | parallel workers; see the warning below |
| `VELOCITY_TEST_SYMBOL`     | `AAPL`                                   | a symbol expected to have inventory |
| `VELOCITY_ILLIQUID_SYMBOL` | unset                                    | a real symbol expected to have none |
| `VELOCITY_UNKNOWN_SYMBOL`  | `ZZZZQQ`                                 | not a real symbol; drives status code 1 |
| `VELOCITY_TEST_QTY`        | `100`                                    | default order quantity |
| `VELOCITY_CALLBACK_URL`    | unset                                    | optional logon `callbackUrl` |

**No credential has a committed default.** The UI suite keeps fallback logins in
`UI-Automation/utils/testdata.js`; this suite deliberately does not, because
these endpoints reach a trading backend and a stray run must not be able to
authenticate on its own.

`.env` is already gitignored if you prefer a file over shell variables.

## Three things worth knowing before you add scenarios

**1. `status.code` 0 does not mean success on an order response.**

Spec 1.9 is explicit: on `/limit`, `/overnight` and `/locate`, read `code` 0
together with `orderStatus`. With a fill (1 or 2) it means "no error"; without
one it means **No Inventory**. A test that asserts `code === 0` and stops will
pass on an order that located nothing. Use the `the order response should
indicate no error` step, or `interpretOrderStatus()` — never a bare comparison.

**2. The suite runs serial on purpose.**

Locate orders consume real dev inventory. Two workers quoting and locating the
same symbol turn a legitimate fill into an intermittent No Inventory, and the
failure looks like a product bug. `API_WORKERS` raises it once a scenario set is
known to be independent.

**3. The `/snapshot` response shape is unconfirmed.**

The spec's printed sample for 1.10 shows an unnamed `{ symbol, offerPx }` object
inside `data`, which is not valid JSON, so the real key is unknown until a live
response is seen. `utils/snapshot.js` accepts any of the plausible readings and
reports which one the server used. Once a real response confirms it, narrow that
helper and tighten `SNAPSHOT_RESPONSE` in `schemas/responseSchemas.js`.

## Findings from the first live call

Only one scenario has been run against dev so far — the credential-free
`A logon document missing required fields is rejected`. It failed, and the
failure is real, not a framework defect:

```
POST /logon  {}   ->  HTTP 500
{"status":{"code":3,"message":"Internal Processing Error"}}
```

Two deviations from the specification in one response:

1. **Wrong HTTP code.** Spec 1.11 assigns missing fields to **400 Bad Request**
   ("The client SHOULD NOT repeat the request without modifications"). The dev
   host returns **500 Internal Server Error**, which per the same section means
   an unexpected server condition — it tells a client to retry when it should
   be telling it to fix the request.
2. **Undocumented status code.** `status.code` 3 does not appear in the spec's
   Status Code list (0, 1, 2, 80, 93–99). It is mapped in `statusCodes.js` so
   failure messages read sensibly, flagged as observed-not-specified.

The assertion has been left as the spec states. The suite's job is to hold the
server to the documented contract, so this stays red until either the server
returns 400 or Velocity confirms the spec is out of date — at which point the
scenario, not the client, is what changes.

The other 76 scenarios are unrun: they need credentials.

## Open questions for Velocity

Carried out of the spec, worth confirming before treating any of these
assertions as settled:

- **400 vs 500 on a malformed or incomplete document**, and the meaning of
  `status.code` 3 — see "Findings from the first live call" above. Applies to
  every endpoint, so `ApiContract.feature` has a scenario outline covering all
  seven.

- **`locateId` type.** 1.4 says it was unified to string across requests and
  responses, previously mixed. The schema asserts `string`; a number is a
  visible failure rather than a silent coercion.
- **Status code 80, Unknown TIF.** The spec notes JSON requests carry no
  time-in-force field, so this should be unreachable over JSON. It is mapped in
  `statusCodes.js` but no scenario provokes it.
- **A stray `orderPx` on `/overnight`.** 1.8 says the request omits it; the
  spec does not say whether sending one is ignored or rejected. One scenario
  probes it and asserts only that the order still comes back as overnight.
- **Which layer reports an invalidated token** — HTTP 401, or HTTP 200 with a
  non-zero status code. The logout scenario accepts either.

## Conventions

- One feature file per endpoint, named after the spec section.
- Tags: `@API` on everything, plus `@Smoke` / `@Regression`, an endpoint tag
  (`@Quote`, `@Limit`, ...) and `@Negative` on failure paths. `@Smoke` is the
  only tag that selects the smoke suite — the same rule as the UI suite.
- Re-run `bddgen` (or use the `npm run test:api*` scripts, which do) after
  editing a feature file or a tag. Stale generated specs are the usual cause of
  "my new scenario did not run".
- Comments in source files are ASCII-only, matching the rest of the repo.
