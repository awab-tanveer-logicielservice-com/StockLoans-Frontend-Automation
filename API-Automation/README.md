# Velocity JSON API automation

Automation for the **Velocity Locate Services JSON API Specification 1.5** — the seven
HTTPS endpoints behind Velocity Locate Services.

This suite targets the **Dev/Test environment only**. The production host is
recorded in `Config/env.js` purely so the guard can refuse it by name: these
scenarios place real locate orders, and `API_BASE_URL` pointing anywhere on
`velocityclearing.llc` throws before the first request.

It lives beside `UI-Automation/` and shares the same runner (Playwright +
playwright-bdd), the same reporter (Allure) and the same Gherkin conventions,
but shares no code with it. Nothing here launches a browser — no step uses the
`page` fixture, so the whole suite runs at HTTP speed.

---

## Quick start

```powershell
# 1. Credentials - no defaults, by design (see "Configuration" below)
$env:VELOCITY_API_USER     = '<preassigned UserID>'
$env:VELOCITY_API_PASSWORD = '<preassigned password>'
$env:VELOCITY_MPID         = '<market participant id>'
$env:VELOCITY_TRADER       = '<trader id>'

# 2. Run
npm run test:api:smoke     # @Smoke scenarios only
npm run test:api           # the full API suite
npm run test:api:ci        # full suite with the Allure reporter
npx playwright test --project=api --grep "The APIs run in the documented order" --workers=1

# Useful one-offs
$env:API_LOG = '1'; npm run test:api        # print every request/response
npx playwright test --project=api --grep @Quote
```

Without the four required variables the authenticated scenarios **skip** rather
than fail, so a run on a machine with no credentials reports honestly instead of
producing a wall of red.

## Configuration

Required — the suite throws naming the variable if one is missing:

| Variable                 | Meaning                                    |
| ------------------------ | ------------------------------------------ |
| `VELOCITY_API_USER`      | preassigned UserID (spec section 3)        |
| `VELOCITY_API_PASSWORD`  | preassigned password (spec section 3)      |
| `VELOCITY_MPID`          | market participant id on quote/order calls |
| `VELOCITY_TRADER`        | trader id on quote/order calls             |

Optional:

| Variable                   | Default                                  | Meaning |
| -------------------------- | ---------------------------------------- | ------- |
| `API_BASE_URL`             | `https://betapi.velocitycapitalllc.com/json` | another dev/test host; production is refused |
| `API_TIMEOUT_MS`           | `30000`                                  | per-request timeout |
| `API_LOG`                  | off                                      | `1` prints every request/response (password and token redacted) |
| `API_WORKERS`              | `1`                                      | parallel workers; see the warning below |
| `VELOCITY_TEST_SYMBOL`     | `AAPL`                                   | a symbol expected to have inventory |
| `VELOCITY_ILLIQUID_SYMBOL` | unset                                    | a real symbol expected to have none |
| `VELOCITY_UNKNOWN_SYMBOL`  | `ZZZZQQ`                                 | unrecognized symbol; drives no-inventory handling |
| `VELOCITY_TEST_QTY`        | `100`                                    | default order quantity |
| `VELOCITY_CALLBACK_URL`    | unset                                    | optional logon `callbackUrl` |

**No credential has a committed default.** The UI suite keeps fallback logins in
`UI-Automation/utils/testdata.js`; this suite deliberately does not, because
these endpoints reach a trading backend and a stray run must not be able to
authenticate on its own.

`.env` is already gitignored if you prefer a file over shell variables.

## Specification 1.5 contract highlights

- Responses use `application/json;charset=utf-8`; requests use
  `application/json`.
- `/logon` returns `time`, tokens expire at 20:01 US Eastern on issuance day,
  and empty/invalid JSON requests return HTTP 401. Missing required logon fields
  return HTTP 500/status code 3.
- `/logout` requires the token in both the query string and JSON body. Its
  success response contains `user` and `status` only.
- `/quote` requires `orderQty`, and `data.id` is always `-1`. Quantities are
  rounded down to round lots of 100; sub-100 requests echo `orderQty: 0`.
- `/snapshot` is firm-wide and is requested with `symbol: "snapshot"`; the
  response echoes `"SNAPSHOT"` and carries the list in `data.items`.
- `/limit` accepts optional string `tif` (`"IOC"` for partial fills; omitted
  or any other value is FOK). Order responses use numeric `locateId` and
  numeric `tif`; `orderStatus` is authoritative.
- `/overnight` can carry only previous-trading-day fills matching symbol,
  trader, MPID, and account. A successful booking is `orderStatus: 2` with
  `status.code: -1`; code 96/orderStatus 8 means there was nothing eligible.
  Repeating an overnight request creates another booking, so the suite makes
  only one successful overnight request per run.
- `/locate` requests require both `cliOrdId` and `locateId`; missing fields
  return HTTP 200/status code 20. Response `locateId` is numeric.
- HTTP 401 may use either the lowercase status envelope or the early
  authentication envelope `{"Status":401,"message":"..."}`. Missing required
  fields are endpoint-specific: `/locate` uses HTTP 200/status 20; quote,
  snapshot, limit, and overnight use HTTP 400; logon uses HTTP 500 for missing
  fields and HTTP 401 for empty/malformed JSON; logout missing fields use
  HTTP 400.

`VELOCITY_API_FINDINGS_2026-10-14.md` records observations made against
Specification 1.4 and is historical; its older response-shape and status-code
expectations are superseded by Specification 1.5.

## Operational notes

- The API workflow is logon → quote → snapshot → limit → locate → overnight →
  logout on one token. The ordered workflow accepts the documented
  `No Prior Locate to Overnight` rejection as a valid API response; it does not
  claim an overnight booking occurred.
- Locate orders consume Dev/Test inventory. The suite runs serial by default;
  increasing `API_WORKERS` can make inventory-dependent results intermittent.
- `/snapshot` returns the documented `data.items` array of `{ symbol,
  offerPx }` entries.

## Conventions

- One feature file per endpoint, named after the spec section.
- Tags: `@API` on everything, plus `@Smoke` / `@Regression`, an endpoint tag
  (`@Quote`, `@Limit`, ...) and `@Negative` on failure paths. `@Smoke` is the
  only tag that selects the smoke suite — the same rule as the UI suite.
- `@RequiresPriorDayFill` marks the single successful
  `OvernightLocateOrder.feature` scenario. Confirmed 2026-10-20: `/overnight` is built from a
  locate that filled on the *previous business day* for the same
  MPID+trader+symbol+account (see `VELOCITY_API_FINDINGS_2026-10-14.md`,
  "Resolved - not a bug", item A) - a precondition a same-day CI run cannot
  satisfy on its own. `npm run test:api` / `test:api:smoke` / `test:api:ci`
  exclude this tag (`--grep-invert @RequiresPriorDayFill`) so the regular
  suite only reports on what it can actually control. Run them deliberately
  with `npm run test:api:overnight`, the day after seeding a limit-locate on
  `VELOCITY_TEST_SYMBOL` (via a `/limit` call - see LimitLocateOrder.feature).
  No automated seeding job exists yet; this is a manual/scheduled step.
- Logout scenarios are part of the default suite and can also be run alone with
  `npm run test:api:logout`; the client sends the required token in both query
  and JSON body.
- Re-run `bddgen` (or use the `npm run test:api*` scripts, which do) after
  editing a feature file or a tag. Stale generated specs are the usual cause of
  "my new scenario did not run".
- Comments in source files are ASCII-only, matching the rest of the repo.
